# 计算中心全能力编排与三中心隔离运行规范

## 1. 固定拓扑

```text
用户
  ↓
GPTs 使用中心（唯一控制者、唯一传输者、唯一跨中心中继）
  ├─ 创建独立 [api] 票据 → 取回并核验 API Snapshot / Manifest / SHA
  ├─ 创建独立 [compute] 票据 → 取回并核验 Compute Result / Preflight / Manifest / SHA
  └─ 创建独立 [execution] 票据 → 取回并核验专家与裁判报告
```

API中心、计算中心、专家团中心同级并列，彼此隔离。任何箭头都必须经过GPTs，不表示中心直接调用。

禁止：

- API中心直接调用计算中心或专家团；
- 计算中心直接调用API中心或专家团；
- 专家团直接调用API中心或计算中心；
- 中心之间下载对方Artifact、读取对方运行目录、派发对方Workflow；
- 以共享数据库、共享运行状态或隐式缓存绕过GPTs中继。

## 2. 断网边界

计算中心的数值与模型运行时：

- 不访问互联网；
- 不取业务数据；
- 不调用语言模型；
- 不下载票据指定代码或依赖；
- 不连接券商、地图、行情、搜索或远程求解器；
- 不联系另外两个业务中心。

`compute_ticket.py` 仅作为GitHub出票控制面访问 `api.github.com`，用途限定为Issue授权、历史状态和重复任务保护。它不进入数值模型，不获取业务数据，不允许任意URL，也不是跨中心通道。

断网不会削弱NumPy、SciPy、SimPy、Mesa、Shapely、PyProj、statsmodels、SALib、OR-Tools、PyPortfolioOpt和vectorbt的本地计算能力；它限制的是实时数据获取、远程模型、在线求解器和动态代码，而这些应由API中心或仓库受控依赖解决。

## 3. “发挥全部能力”的含义

不是每个问题把所有算法同时运行一遍。正确方式是由GPTs根据问题结构选择一条或多条受控计算链，并在关键结论上做交叉验证。

### 不确定性链

```text
描述统计
→ 假设验证
→ 局部敏感性或Sobol全局敏感性
→ 蒙特卡罗
→ 情景比较或最小后悔
```

### 商业经营链

```text
单位经济 / 盈亏平衡
→ 时间序列预测
→ 蒙特卡罗需求与成本
→ 约束优化或混合整数规划
→ 压力测试
→ MCDA决策排序
```

### 物流与运力链

```text
GIS坐标与距离处理
→ 排队/离散事件仿真
→ 智能体仿真
→ 指派优化或车辆路径
→ 拥堵与极端情景压力测试
```

实时地图、路线、人口、天气或订单代理数据必须先由GPTs通过API中心取得并核验，再生成新的计算票据。

### 金融研究链

```text
收益风险指标
→ 因子回归
→ 走样本外回测
→ 风险平价或组合优化
→ 压力测试
→ 资本预算 / 情景 / 最小后悔
```

不取实时行情、不执行交易、不保证收益。GPTs必须明确数据截止时间、复权方式、频率、费用、滑点和样本外区间。

### 战略与情报链

```text
竞争假设分析
→ 证据可靠性与诊断性评分
→ 指标与预警
→ 博弈或智能体推演
→ 情景比较 / 最小后悔 / 信息价值
→ 专家团解释与红队
```

计算中心只处理GPTs提交的结构化证据和评分，不自行搜集情报，也不把结构化评分等同于事实真相。

## 4. 严格数据缺口处理

每次计算生成 `compute-data-gap-plan.json`。计算中心只识别缺口和输出GPTs行动计划，不执行任何补数动作。

GPTs按以下顺序处理：

```text
独立API票据取得观测值
→ 请求用户真实记录
→ 保存并核验公开资料快照
→ 同来源历史数据
→ 同地区/同时段/同业务基准
→ 明确代理变量
→ 区间或概率分布假设并取得必要批准
→ 仍无依据则保持 DATA_INSUFFICIENT
```

禁止静默填零、均值填充、删除样本或编造单点。低置信度参数必须给区间/分布；结论对其敏感时，不得输出无条件唯一建议。

任何数据、假设或批准发生变化后，GPTs必须创建新的计算票据，不能让计算中心自行修改原票据。

## 5. 专家解释与红队

计算成功后生成 `compute-expert-review-request.json`。该文件只是给GPTs的交接模板，不会直接派发专家团。

GPTs取回并核验以下文件后，才可创建新的 `[execution]` 票据：

- `compute-preflight.json`；
- `compute-result.json`；
- `compute-audit.json`；
- `compute-diagnostics.json`；
- `artifact-manifest.json`。

专家团任务限定为：

1. 解释数值结果与决策含义；
2. 红队数据来源、假设、模型形式和遗漏变量；
3. 找出会使结论反转的参数和阈值；
4. 比较替代解释和不利情景；
5. 明确适用边界、失效条件和需要继续取得的证据。

专家团不能修改计算结果，也不能直接向计算中心回写。若专家提出新假设，必须返回GPTs，由GPTs结构化并在必要时取得用户批准，再创建新的计算票据。

## 6. 全能力验收

正式全量验收必须同时满足：

- 三中心隔离静态审计PASS；
- 计算中心完整单元和集成测试PASS；
- 20个production operation逐项通过生产调度；
- Decision Intelligence V2全部22个模式逐项通过生产调度；
- 每项均证明 `network_used=false`、`model_calls=0`；
- 每项Result、Preflight、Data Gap Plan、Expert Review Request、Audit、Diagnostics和Manifest齐全；
- 汇总哈希和逐项包哈希可核验。

工作流：`.github/workflows/compute-all-operations-validate.yml`。

只有出现 `20/20 operations PASS` 和 `22/22 modes PASS`，才能声明当前固定能力全部跑通。代码合并、单元测试通过或只跑一次蒙特卡罗都不足以证明全能力验收。
