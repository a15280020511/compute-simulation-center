# 计算中心准确性闭环与机构库运行规范

## 一、十六类机构库

计算中心使用仓库内版本化注册表，不运行数据库服务器，不保存数据库凭据，不允许任意SQL。

1. 模型库：模型用途、版本、工程成熟度、证据成熟度、失效条件和退役。
2. 方法库：固定算法、求解器、依赖、适用范围和回滚。
3. 策略库：期望值、最小后悔、稳健决策、适应性路径、信息价值、组合分散、阈值响应和满意解。
4. 规则库：不可绕过、失败关闭的机构级规则。
5. 假设库：已批准、版本化、可证伪且有有效域的机构假设。
6. 分布与先验库：允许的分布、先验、参数要求和使用边界。
7. 参数与校准库：参数定义、观测、边界、多起点、可识别性和验证要求。
8. 约束库：硬约束、软约束、求解器内约束和独立结果复核。
9. 场景库：基准、压力、逆向压力、反事实、对抗和边界场景。
10. 机制覆盖库：关键机制、遗漏、替代结构和失效机制。
11. 实验设计库：种子、实际重复次数、停止规则、留出、多起点和步长敏感性。
12. 数据与证据库：冻结数据快照、来源、时间、单位、范围和SHA-256。
13. 样本库：总体、抽样方法、代表性、偏差、许可和快照引用。
14. 基准与验证库：解析真值、参数恢复、冻结真实、对抗、交叉实现和影子运行。
15. 可信度库：按具体用途逐因素评估，不使用魔法总分。
16. 反馈与结果库：预测、真实结果、误差、漂移、缺陷和生命周期事件。

这些库的作用是提供经过治理的候选材料和质量规则，不是预先存放“现实真相”。

## 二、数据不足时的假设机制

固定顺序：

```text
API或行政观测
→ 用户真实记录
→ 带哈希的公开证据快照
→ 同定义历史样本
→ 已批准基准样本
→ 明确代理变量
→ 经批准的区间或概率分布
→ 仍不足则停止
```

计算中心不得：

- 静默填零；
- 静默使用均值或中位数；
- 把模型生成值当观测；
- 把代理值、插补值或合成值改写成真实样本；
- 在没有范围和失效条件时制造一个单点；
- 在结论对假设敏感时给出无条件唯一建议。

每个假设必须记录：

- 假设名称和类型；
- 使用原因；
- 来源类型；
- 置信度；
- 区间或分布；
- 证据哈希；
- 适用范围；
- 证伪测试；
- 失效条件；
- 批准人；
- 复核日期。

`compute-assumption-plan.json`只提出候选范围和补数行动。正式或高风险任务有未解决候选时直接阻断，GPTs必须补证据或取得批准后创建新票据。

## 三、正式运行链

```text
票据和来源校验
→ 数据就绪预检
→ 假设计划与假设治理
→ 模型和方法注册校验
→ 原始输入硬约束
→ 多起点参数校准
→ 校准后输入硬约束
→ 按实验设计实际重复运行
→ 正式求解
→ 独立结果约束复核
→ 样本外验证与简单基线比较
→ 残差、偏差、相关和尾部诊断
→ 工程成熟度与证据成熟度判定
→ 质量放行
→ Artifact、哈希和反馈登记
```

## 四、参数校准

提交校准配置时必须同时提交：

- 冻结观测值；
- 观测快照哈希；
- 参数对应的固定输入路径；
- 参数初值和上下界；
- 固定结果提取路径；
- 校准目标；
- 多起点数量和随机种子；
- 可选验证观测。

运行器实际调用仓库内固定operation，改变允许参数，比较预测与观测并选择最佳可行结果。输出参数、区间、RMSE、MAE、偏差、可识别性、多起点结果和验证误差。

只通过Schema而没有真正拟合时，不再标记为已校准。

## 五、随机仿真的验证

票据声明重复次数后，中央实验执行器必须真实执行相同次数，并保存：

- 每次种子；
- 请求和实际执行次数；
- 跨运行均值、中位数、方差；
- Monte Carlo标准误；
- 95%置信区间；
- 精度停止规则是否满足。

声明30次但实际只运行1次属于失败。

## 六、结果验证

最终结果按任务类型选择：

- 普通预测：留出集或滚动时间窗；
- 时间序列：rolling-origin或blocked holdout；
- 地理模型：空间分组留出；
- 参数模型：参数恢复；
- 新模型：影子运行；
- 复杂模型：必须与简单基线和替代结构比较。

验证指标包括RMSE、MAE、偏差、Brier、ECE、log loss、区间覆盖率和决策损失。

复杂模型不能稳定胜过简单基线时，标记`CANDIDATE_DID_NOT_BEAT_BASELINE`，不得因为复杂而优先使用。

## 七、真实结果反馈

决策时冻结：

- 预测和概率；
- 预测区间；
- 模型和参数版本；
- 输入、样本、假设和证据哈希；
- 决策时间和适用域。

真实结果到达后创建新的反馈票据，计算：

- 预测误差；
- 概率校准；
- 区间覆盖；
- 系统偏差；
- 数据和性能漂移。

失败时触发重新校准、重新验证或模型降级；旧结果保持不可变，禁止覆盖历史。

## 八、成熟度与放行

工程成熟度回答模型能否安全稳定运行；证据成熟度回答模型是否足以支持现实决策。

- experimental：只有基础运行或少量测试。
- controlled-preview：有部分基准或验证，但证据不完整。
- production：有校准、样本外验证、重复实验和批准基准。
- decision-grade：在具体使用域有真实反馈和独立技术审查。

默认要求：

- exploratory：experimental即可；
- formal：至少production；
- high_stakes：必须decision-grade。

证据不足时可以保留计算结果供研究，但质量状态为`DECISION_BLOCKED`，不得作为正式决策结论。

## 九、发布和隔离

依赖在联网阶段安装，数值执行进入Linux network namespace后运行，并先生成`compute-network-assurance.json`。

默认发布策略为`artifact_only`：Issue只包含状态、成熟度、结果哈希和Artifact引用；完整输入与结果不公开粘贴。只有票据明确设置`public_result`时才允许公开完整结果。
